## 1. Key 校验判定（T3/T7 服务端，P2）
- 现象：6000D 网关未开 require_key，对不带 Key、带假 Key 的请求都回 200；服务 `probe_connection` 据此报 `key_valid: true`，界面对**假 Key** 也显示"Key 有效"。这会让律师在 Key 填错时毫无感觉，等甲方一开校验就全体失败。
- 改法：探测时**多发一次带明显无效 Key 的请求**（如 `Bearer invalid-<随机>`）：若它也 200 → 网关未校验 → `key_valid: null`，message 加"网关当前未校验 Key，无法确认 Key 是否正确"；若它 401/403 而真 Key 200 → `true`；真 Key 401/403 → `false`。契约 `connection_test.schema.json` 已允许 null，不改契约。加用例三态；假 6000D 加"不校验"模式。
- 顺带：测试连接对 6000D 显示"0 毫秒"——`latency_ms` 取法看是不是在 `net.select` 之后才起表；改为覆盖真实请求耗时。
