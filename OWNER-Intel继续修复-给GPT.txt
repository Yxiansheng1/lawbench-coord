二、缺陷 A：签名脚本漏签 Electron Framework

现象：
  连越律所AI工作台.app/Contents/Frameworks/Electron Framework.framework/Versions/A/
    Electron Framework: code object is not signed at all

判断：
  sign-adhoc.sh 第 1 步用
    find ... -type f \( -name '*.dylib' -o -name '*.so' -o -name '*.node' -o -perm -u+x \)
  来挑可执行文件。-perm -u+x 在 BSD find 下要求「所有指定位都置位」，
  Electron Framework 这个主二进制的权限位与普通可执行文件不同，没被匹配到，
  因此从未被签名。

  第一次失败（Helper (Renderer) 未签）和这次（Electron Framework 未签）
  是同一类问题的两次暴露：靠「文件名模式 + 权限位」挑文件，挑不全是必然的。

修法要求：
  第 1 步改成不依赖权限位的全量扫描：
  1. 遍历 $APP/Contents 下所有普通文件
  2. 对每个文件跑 file -b，输出含 Mach-O 的就 sign
  3. 仍排除 Contents/Resources/tools/LibreOffice.app/** 与
     Contents/Resources/app.asar.unpacked/**
  4. 主可执行文件（CFBundleExecutable）仍推迟到最后显式签一次（保留你已做的修法）
  不许用 --deep 走捷径，不许删掉最后的 codesign --verify --strict。

三、缺陷 B：x64 包里混进 arm64 二进制（这条更要紧）

现象：x64 构建日志里出现
  .../Resources/runtime/primary-runtime/dependencies/pnpm/dist/node_modules/
    @reflink/reflink-darwin-arm64/reflink.darwin-arm64.node: replacing existing signature

在 x64 构建里出现了 arm64 的 .node。

为什么比签名严重：
  签名失败是构建层错误，看得见。
  架构混入是产物层错误，可能签得过、装得上、运行时才崩。
  这是最容易「看起来成功、实际交付出去是坏的」的一类问题。

五、架构清单怎么查

对连越律所AI工作台.app/Contents 下所有下列文件跑 file -b 或 lipo -info：
  · 所有 *.node
  · 所有 *.dylib
  · 所有 *.so
  · Contents/MacOS/** 下所有文件
  · Contents/Frameworks/** 下所有文件
  · Contents/Resources/runtime/** 下所有可执行文件
  · Contents/Resources/python/** 下的解释器与扩展模块

输出清单：每个文件的路径 + 架构（arm64 / x86_64 / universal）

判据：
  全部 x86_64 或 universal  → 架构没问题，只修缺陷 A
  有 arm64 混入            → 必须先修，修完再谈签名

如果确认有混入，要查的是「为什么 x64 构建会装 arm64 的包」。方向：
  · pnpm 在 mac-x64 目标下是否装了两个架构的可选依赖
    （optionalDependencies 里的 darwin-arm64 / darwin-x64 双份）
  · packaging/mac/build.sh 里安装 Node 运行时依赖那一步，架构参数有没有传对
  · @reflink 这类带平台后缀的包，是否被当作普通依赖全量安装了

不许用「删掉整个 @reflink」来回避——先确认这个包是干什么的、被谁用。
