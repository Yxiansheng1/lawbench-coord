## 为什么带入、由谁使用

本机 pnpm 为 11.7.0，内嵌 `@reflink/reflink` 0.1.19 的 darwin-arm64 与 darwin-x64 原生模块。两个复制入口都未过滤架构：
- `dsh/apps/desktop/scripts/prepare-runtime.ts` 的 `preparePnpm()` 直接 `cpSync(packageDir, destination, { recursive: true })`，生成 `runtime/pnpm`。
- `dsh/scripts/primary-runtime/prepare.ts` 直接 `cp(dirname(pnpmManifest), dependencies/pnpm, { recursive: true, dereference: true })`，生成 `runtime/primary-runtime/dependencies/pnpm`。
上述复制路径解释了日志中的两份 ARM 文件；不是据此认定 Node/Python/Electron 主体都选错架构。尚未拿到失败 app 的完整模块表，不能排除其它混入点。
`@reflink` 提供文件克隆/复制操作，pnpm 的 `createCloneFunction()` 调用 `reflinkFileSync`，worker 中也有调用。`binding.js` 在 darwin 上先尝试 universal，再依据 `process.arch` 选择 x64 或 arm64。双份文件存在不等于已证实 x64 运行时加载了 ARM，但不满足 owner“产物不得含 arm64 专属二进制”的验收条件。整个 @reflink 不能删除。
